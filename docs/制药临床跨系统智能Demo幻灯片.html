典型场景

某药品批次运输途中出现温度偏移，质量部门需要立刻知道：
这个批次发到了哪些研究中心？哪些受试者实际用了它？
其中谁发生了严重不良事件？

回答它需要依次查供应链运单 → CTMS 受试者归属 → EDC 给药记录 → 安全数据库不良事件。

今天的现实

  • 四个系统、四拨人、四次取数，通常以天为单位
  • 系统之间既没有统一业务语言，也没有现成关联路径
  • 而这类问题往往有时限要求（质量事件、安全信号评估）
  • 人工拼接的结果难以复现，无法满足 GxP 审计追溯

两类边，是证据可信度的基础

Graph — 算得对

  • 多跳路径、可达性、影响面是图原生能力
  • 实时遍历，不是固化报表
  • 新增一类关系不需要重建数据模型

Ontology — 说得清、管得住

  • 术语与口径治理："严重不良事件""重要方案偏离""证据等级"定义在语义层，可审计
  • 跨源统一：同一个"受试者"在 CTMS / EDC / Safety 里被绑定为同一实体
  • 同义词映射："病人""患者""入组对象"指向同一概念

Data Agent — 问得方便

  • 业务用户不需要知道表在哪、字段叫什么
  • 回答附带证据等级、置信度、数据版本
  • 通过 MCP 端点开放给外部 AI 应用调用

定位提醒：不要把 Ontology 说成"路径查询的必需组件"——客户会追问不用它行不行。正确说法是：Graph 负责算得对，Ontology 负责说得清、管得住、能复用。

四条链路跳数完全相同

只看"最短路径"根本区分不出来。真正的业务判断依赖证据折损：代谢通路解释优于主靶点解释。

口径定义在语义层

证据折损 = (1 − 置信度) + 证据等级惩罚；A 级 0、B 级 0.05、C 级 0.15、D 级 0.30，越小越强。

先看最弱环节

同时给出最差证据等级与最低置信度——审评场景里人先看短板，再看总分。

证据折损是来自图算法边权重的无量纲不确定度指标，与费用、预算、资源投入无关。

Q4 · 同靶点风险外推

SYN-101 与 SYN-102 共享 Janus 激酶 1 靶点及 JAK-STAT、骨髓造血两条通路，可能共享药物性肝损伤、中性粒细胞减少症等风险 —— 支持管线层面提前布防，而不是事后补救。

确定性，是受监管行业能否落地的前提：路径与风险分由 BFS、Dijkstra 和确定性公式计算，不是模型打分。同样的输入永远得到同样的输出，可复现、可审计、可解释。图逻辑单一来源（fabric/graph_logic.py），本地先验证再上云，笔记本末尾写死断言，杜绝"跑成功了但表是空的"。

总结

从"跨四个系统、等两三天"
到"一句中文、几秒钟"

① 全链路在一个平台内完成

六个源系统落地、统一、图建模、语义层、AI 问数全在 Fabric 内，OneLake 是唯一副本，无第三方图数据库。

② 图是原生能力，不是外挂

1555 节点 / 2950 边，价值集中在跨源的那 8 类关系上。

③ 语义层让口径可治理

"最佳路径""严重不良事件"的定义写在本体里，而非散落于各报表 SQL 与提示词，满足 GxP 审计。

④ 结果确定、可复现、可审计

确定性算法 + 落地断言 + 中文回归测试集，演示答案稳定。

建议演示节奏（20 分钟）

① 先给冲击力：Q2 批次溯源（5 min） → ② 图原生能力：门户 GQL 实时多跳（5 min） → ③ 证据深度：Q1 跳数相同、折损不同（5 min） → ④ 治理与扩展：Ontology 跨 5 系统绑定 + Q4 风险外推（5 min）
