# CRF 到 SDTM 映射血缘 Demo 演示手册

面向临床数据管理与统计编程团队。全部数据为**示意性合成数据**，SDTM 域名与变量名仅
参考公开的 CDISC 命名习惯，不含任何真实研究、真实映射规范或客户资料。

---

## 一、这个 Demo 解决什么问题

一份 CRF 到 SDTM 的映射规范，本质上是一张**关系网**：一个 CRF 字段流向哪些标准变量，
一个标准变量又是从哪几处汇集而来，改一处会牵动多远。

今天这张网存在于 Excel 里。Excel 能存关系，但不能**查**关系：

| 业务动作 | 在 Excel 里 | 需要的能力 |
|---|---|---|
| 这个变量到底从哪来的 | 全表搜变量名，人工排重 | 反向溯源 |
| 改这一栏会连累谁 | 逐行看，容易漏掉多跳 | 正向影响分析 |
| 版本升级改了什么 | 两份文件肉眼比对 | 版本差异 |
| 哪些该交的还没采 | 拿标准清单人工核对 | 覆盖率检查 |
| 补充数据集里的能不能挪回去 | 凭经验判断 | 治理决策支持 |

这五件事的共同点：**都是图上的问题**，而不是表格里的问题。Excel 的行列结构表达不了
"顺着关系走几步"，所以每一次都得靠人在脑子里补上这个能力。

Demo 要证明的是：把这张网放进 Fabric，业务用户可以直接用自然语言问，而不需要懂
表结构、不需要写查询、也不需要知道什么是图。

## 二、两层设计：只做规范层，不做实例层

这是本方案最关键的取舍，也是成本能不能控住的分界线。

```
规范层图（本 Demo 采用）
  内容：CRF 字段与 SDTM 变量之间的映射规则
  规模：百级节点、百级边，随规范版本变化，不随受试者增长
  回答：应该怎么映射、改一处影响谁、哪条路径最直接

实例层血缘（本 Demo 不做）
  内容：某一条具体记录的实际来源
  规模：随受试者数、访视数、检验项线性膨胀，百万级起
  代价：图索引成本与刷新时间失控，且业务上并不需要
```

映射规范一共几百条规则，是**稳定的、可枚举的、值得建图的**。而"某位受试者第 3 次访视
的 ALT 值来自哪条原始记录"属于审计追踪，数据库自身的稽查轨迹已经覆盖，不该由图承担。

演示时如果客户问"能不能追到每一条数据"，答案是：**能，但不该在这层做**。这个回答比
"能"更有说服力，因为它说明我们理解成本边界。

## 四、映射折损：为什么需要这个指标

多条路径都能到达同一个变量时，业务用户真正想知道的是"**哪条最可信**"。跳数少不等于
可信：一次条件赋值可能比两次直接拷贝更需要人工解释。

所以给每种转换方式一个权重，路径的可信度就是权重的累加：

| 转换方式 | 单跳折损 | 含义 |
|---|---:|---|
| Copy | 0.02 | 原样拷贝 |
| CopyUpcase | 0.03 | 拷贝并转大写 |
| Assigned | 0.05 | 赋常量，不依赖源字段取值 |
| DT2DTC | 0.10 | 日期转 ISO8601 |
| Lookup | 0.15 | 查外部字典 |
| IfAssigned | 0.20 | 按条件分支赋值 |
| Coding | 0.25 | 医学编码，依赖词典版本 |
| Derived | 0.30 | 由多个变量计算得出 |
| 额外：落在补充限定符域 | +0.15 | |
| 额外：目标变量无受控术语约束 | +0.10 | |

**必须向客户说清的一点**：折损是无量纲权重，衡量"这次转换需要多少人为解释"，
**与金额、工时、预算没有任何关系**。演示时如果被理解成成本估算，整个指标就失去意义。

本次规范中各转换方式的实际使用次数（按单跳统计）：

| 转换方式 | 次数 | 其中映射 | 其中派生 |
|---|---:|---:|---:|
| Copy | 18 | 18 | 0 |
| DT2DTC | 17 | 17 | 0 |
| Derived | 17 | 0 | 17 |
| CopyUpcase | 15 | 15 | 0 |
| IfAssigned | 7 | 7 | 0 |
| Lookup | 6 | 5 | 1 |
| Coding | 4 | 0 | 4 |
| Assigned | 3 | 3 | 0 |

## 五、六个业务问题与实测结果

以下问题按业务用户的实际说法提出，不含任何表名或技术词汇，全部经实测。

### 问题一 · 反向溯源

> 治疗组这个信息，最后交出去的数据集里是从哪张表单哪一栏来的？如果有好几个来源，哪个最直接？

**实测结果**：`DM.ARMCD` 有两条来源

| 排名 | 来源字段 | 转换方式 | 折损 | 适用条件 |
|---:|---|---|---:|---|
| 1 | 分配的治疗组 | Copy | 0.02 | 默认 |
| 2 | 队列 | Lookup | 0.15 | 由队列反查治疗组，仅在未随机化研究使用 |

**演示要点**：两条来源不是优劣关系，而是**适用条件不同**。系统不仅排了序，还给出了
区分依据。这正是 Excel 做不到的：多条规则并列时，人得自己判断哪条适用。

---

### 问题二 · 影响分析

> 我们打算把给药开始日期这一栏改掉，会连累到哪些数据集？改完要重新核对哪些东西？

**实测结果**：影响 6 个变量，跨 5 个域（AE、DM、DS、EX、LB），最长 3 跳

最长链路：
```
给药开始日期 → EX.EXSTDTC 给药开始日期 → DM.RFSTDTC 研究参考开始日期 → DM.AGE 年龄
```

**演示要点**：`DM.AGE` 距离改动点有三跳，人工排查时最容易漏掉的正是这类。研究参考
开始日期是所有研究日计算的基准，一改动会连带 `AE.AESTDY`、`DS.DSSTDY`、`LB.LBBLFL`
一起偏移。这就是"多跳"的价值所在。

影响面排名前几位的字段：

| 表单 / 字段 | aCRF 页 | 影响变量数 | 涉及域 | 最长跳数 |
|---|---:|---:|---|---:|
| 研究药物给药 / 给药开始日期 | 16 | 6 | AE、DM、DS、EX、LB | 3 |
| 实验室检查 / 检验结果 | 18 | 4 | LB | 4 |
| 知情同意 / 知情同意签署日期 | 1 | 3 | DS | 2 |
| 入组 / 入组日期 | 5 | 3 | DS | 2 |

---

### 问题三 · 版本对比

> 这次标准版本升级，映射规则到底改了哪些地方？

**实测结果**：V1 到 V2 共 4 处变化

| 变化类型 | 涉及 | 详情 |
|---|---|---|
| V2 新增 | `IC.RICFDAT` → `DS.DSSTDTC` | DT2DTC，新增再次知情同意日期 |
| V2 新增 | `IC.RICFYN` → `DS.DSDECOD` | IfAssigned，新增再次知情同意标志 |
| 算法变更 | `EN.SFREAS` → `DS.DSDECOD` | Lookup 改为 Assigned |
| V2 移除 | `EN.SCRNPREV` → `SUPPDS.QVAL` | 原为 CopyUpcase，已移除 |

**演示要点**：算法变更那条最值得讲。从 Lookup 改成 Assigned 意味着不再查字典而是
直接赋值，**下游取值范围可能收窄**，但两个版本的 Excel 肉眼比对只会看到算法列的一个
单词变了，很难意识到这个后果。

---

### 问题四 · 覆盖缺口

> 还有哪些该交的字段目前根本没人采？哪些是必须要有的？

**实测结果**：6 项真实缺口

| 优先级 | 变量 | 说明 |
|---|---|---|
| 必填 | `SUPPAE.QVAL` | 必填变量缺少来源，需补充映射或确认采集方式 |
| 预期 | `AE.AETOXGR` 毒性分级 | 建议确认是否适用于本研究 |
| 可选 | `AE.AECONTRT` 是否采取其他治疗措施 | 未映射通常可接受 |
| 可选 | `CM.CMDOSFRQ` 给药频次 | 同上 |
| 可选 | `EG.EGMETHOD` 检查方法 | 同上 |
| 可选 | `VS.VSPOS` 测量体位 | 同上 |

**演示要点**：这里刻意**排除了系统赋值变量**。`STUDYID`、`DOMAIN`、`USUBJID` 这类
本来就不由 CRF 采集，如果一并报进缺口，清单会从 6 条膨胀到 33 条，真正需要跟进的
1 条必填缺口就被淹没了。一个报满屏假缺口的工具，数据管理员看一眼就不会再用。

---

### 问题五 · 补充限定符治理

> 有些数据被放进了所谓的补充数据集，这是什么意思？这些数据有没有可能挪回正式数据集？

**实测结果**：2 项上提候选

| 补充域 | 父域 | QNAM | 来源路径 | 折损 |
|---|---|---|---|---:|
| SUPPDM | DM | COHORT | 队列 → SUPPDM.QVAL | 0.28 |
| SUPPDS | DS | DSPROTVS | 知情的方案版本 → SUPPDS.QVAL | 0.28 |

**演示要点**：0.28 的折损里有 0.15 来自"落在补充限定符域"这一项。上提到标准域后这部分
折损直接消失，下游消费也不必再做一次 SUPP 转置。这是把治理判断**量化**的例子。

---

### 问题六 · 变更风险排序

> 哪几栏一改动牵连最大？我想先把风险最高的几个盯住。

**实测结果**：见问题二的排名表。系统还给出了两类不同的风险形态：

- **跨域广**：给药开始日期，横跨 5 个域，牵一发动全身
- **域内深**：检验结果，只在 LB 域内但链条 4 跳
  （`LBORRES` → `LBSTRESC` → `LBSTRESN` → `LBNRIND`）

**演示要点**：这两类风险的应对方式不同。前者要跨团队协调，后者要盯住派生程序的
计算链。工具把"风险"拆成了可行动的两种。

## 六、Fabric 三种能力的分工

Demo 里三个数据源各有明确职责，不是堆砌。

| 数据源 | 承担什么 | 为什么必须是它 |
|---|---|---|
| **Lakehouse（SQL）** | 五类预先算好的治理结果表 | 问题固定、要求稳定复现，预计算最快最省 |
| **Graph（GQL）** | 结果表未覆盖的任意关系探索 | 变长路径遍历用 SQL 写不出来，也算不动 |
| **Ontology** | 概念是什么、概念之间什么关系 | CDISC 是国际标准词汇，业务说法与标准名之间需要一层映射 |

### 为什么这个场景特别适合 Ontology

在企业自有数据模型上，本体的价值有时只体现在"给字段起个中文名"。但 CDISC 不同：
**SDTM 域、变量、受控术语是一套国际公认的标准词汇**。业务用户说"受试者的处置结论"，
标准名是 `DS.DSDECOD`；说"补充数据集"，标准名是补充限定符域。本体把这层对应关系
显式建模，用户就不必先学会标准术语才能提问。

本体已实例化：**287 个实体**，其中 SDTM 变量 102 个、CRF 字段 59 个，
变量与术语集之间的引用关系可查。

### 图上能问、结果表答不了的问题

```gql
-- 从一个字段出发，四跳以内能触及哪些标准变量
MATCH p = (f:SpecNode WHERE f.NodeId = 'CRF:IC.ICDAT')
  -[:SPEC_RELATIONSHIP]->{1,4}
  (v:SpecNode WHERE v.NodeType = 'SDTMVariable')
RETURN v.DisplayNameZh AS 受影响变量, size(edges(p)) AS 跳数
ORDER BY 跳数 DESC LIMIT 20;
```

变长路径 `{1,4}` 是图查询独有的表达。同样的语义用 SQL 需要写多层自连接，且跳数上限
一变就得重写。

## 七、演示动线（约 20 分钟）

| 时长 | 内容 | 目的 |
|---:|---|---|
| 2 分钟 | 展示映射规范的 Excel 形态，说明五类问题 | 建立共同认知 |
| 2 分钟 | 说明两层设计，规范层与实例层的取舍 | 打消成本顾虑 |
| 5 分钟 | 问题一、问题二（溯源 + 影响分析） | 最直观的价值 |
| 3 分钟 | 问题三（版本对比），重点讲算法变更的后果 | 展示深度 |
| 3 分钟 | 问题四、问题五（缺口 + 治理） | 展示主动发现问题的能力 |
| 3 分钟 | 图上任意关系探索，展示 GQL | 说明能力边界之外还有余量 |
| 2 分钟 | 三种能力分工与落地路径 | 收尾 |

### 演示时必须说清的三件事

1. **数据是合成的**。每次回答结尾都会自动带这句提示。
2. **折损不是钱**。它是不确定度权重，容易被误解成成本估算。
3. **规范层不是实例层**。追每一条记录是稽查轨迹的职责，不该由图承担。

## 八、已知限制

| 限制 | 影响 | 处理方式 |
|---|---|---|
| 图数据源在 MCP 编程接口下报"访问令牌无效" | 用脚本调用时图问题无法回答 | 门户交互会话内正常；自动化改用 GQL Query API 直连 |
| 本体索引需在源表重写后手动刷新 | 数据更新后本体可能查不到 | 部署脚本已包含刷新与实例化校验 |

**关于第一条**，`executeQuery` API 可直接调用，因此自动化路径是通的：

```
POST https://api.fabric.microsoft.com/v1/workspaces/{ws}/GraphModels/{id}/executeQuery?preview=true
{"query": "MATCH ...;"}
```

## 九、落地路径建议

| 阶段 | 内容 | 前提 |
|---|---|---|
| 第一步 | 把现有映射 Excel 按本 Demo 的七张表结构导入 | 需统一列名口径 |
| 第二步 | 跑通五类治理结果表，与人工核对结果比对 | 验证口径一致 |
| 第三步 | 接入规范版本管理，每次发版自动出差异报告 | 需版本号规范 |
| 第四步 | 把影响分析嵌入 CRF 变更评审流程 | 需流程配合 |

第二步是**关键验证点**：如果系统算出的缺口清单与数据管理员人工核对的结果一致，
后面的自动化才有信任基础。
