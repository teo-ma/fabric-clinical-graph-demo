方案设计 · 关键取舍

只做规范层，不做实例层

本方案采用

规范层图

  • 内容：CRF 字段与 SDTM 变量之间的映射规则
  • 规模：百级节点、百级边
  • 增长：随规范版本变化，不随受试者增长
  • 回答：应该怎么映射、改一处影响谁、哪条路径最直接
本方案不做

实例层血缘

  • 内容：某一条具体记录的实际来源
  • 规模：随受试者数、访视数线性膨胀，百万级起
  • 代价：索引成本与刷新时间失控
  • 更合适的位置：数据库自身的稽查轨迹已覆盖

映射规范一共几百条规则，稳定、可枚举、值得建图。而"某位受试者第 3 次访视的 检验值来自哪条原始记录"属于审计追踪，不该由图承担。 这条边界决定了方案的成本能不能控住。

核心指标

映射折损：让「哪条来源最可信」变成一个可比的数

多条路径都能到达同一个变量时，业务用户真正想知道的是哪条最可信。 跳数少不等于可信：一次条件赋值可能比两次直接拷贝更需要人工解释。 于是给每种转换方式一个权重，路径可信度就是权重累加。

单跳折损

Copy 原样拷贝0.02
CopyUpcase 拷贝转大写0.03
Assigned 赋常量0.05
DT2DTC 日期转标准格式0.10
Lookup 查外部字典0.15
IfAssigned 条件分支赋值0.20
Coding 医学编码0.25
Derived 计算派生0.30

额外加权

落在补充限定符域+0.15
目标变量无受控术语约束+0.10

必须说清的一点

折损是无量纲权重，衡量「这次转换需要多少人为解释」， 与金额、工时、预算没有任何关系。 一旦被理解成成本估算，这个指标就失去意义。

价值在哪

两条来源不是优劣关系，而是适用条件不同。系统不仅排了序，还给出了区分依据。 这正是表格做不到的：多条规则并列时，得靠人自己判断哪条适用，而判断依据往往只写在 某一列的备注里，甚至只在某个人的记忆里。

算法变更那条最值得看

从 Lookup 改成 Assigned，意味着不再查字典而是直接赋值，下游取值范围可能收窄。 但两个版本的表格肉眼比对，只会看到算法列的一个单词变了——很难意识到这个后果。

Ontology · 标准词汇

SDTM 域、变量、受控术语是国际公认标准词汇，本体把业务说法与标准名对应起来。

为什么这个场景特别适合本体

在企业自有数据模型上，本体的价值有时只体现在「给字段起个中文名」。但 CDISC 不同—— 它是国际标准。业务用户说「受试者的处置结论」，标准名是 DS.DSDECOD； 说「补充数据集」，标准名是补充限定符域。本体把这层对应显式建模， 用户就不必先学会标准术语才能提问。 已实例化 287 个实体。

变长路径是图查询独有的表达

问：从一个字段出发，四跳以内能触及哪些标准变量

MATCH p = (f:SpecNode WHERE f.NodeId = 'CRF:IC.ICDAT')
  -[:SPEC_RELATIONSHIP]->{1,4}
  (v:SpecNode WHERE v.NodeType = 'SDTMVariable')
RETURN v.DisplayNameZh AS 受影响变量, size(edges(p)) AS 跳数
ORDER BY 跳数 DESC;

小结

把关系网交给能查关系的引擎

规范层，不是实例层

几百条规则值得建图，百万条记录交给稽查轨迹。成本边界清晰。

业务语言，不是表结构

用户不需要知道表名、不需要写查询、也不需要知道什么是图。

三种能力，各有职责

固定问题用 SQL，关系探索用 GQL，概念理解用本体。

本演示全部使用示意性合成数据。所有数字均为实测结果，可复现。 映射折损为无量纲权重，与金额、工时、预算无关。
